# EP.04 · 《装修队的血泪史》

> 🎬 漫画：[EP.04.svg](./EP.04.svg) ｜ 📄 对应文档：[第 4 章 · 渲染性能优化：让每一帧都丝滑](../docs/04-rendering)
>
> 本话主旨：渲染管线的成本阶梯——读写分离、优先 transform/opacity、合成层省着用。

## 本话剧情

小奔兼职装修监工，发现装修工人改一面墙要来回量几十次：量一次改一次，天天返工。稳叔点破：这就是浏览器里的布局抖动——读一次布局改一次样式，每次都要全屋重算。三人总结出装修三原则：先量完再统一改（批量读写）、换窗帘别搬家具（transform/opacity 不触发重排）、常改的东西单独放间房（合成层）——但房间开太多，电工也跑断腿。

## 知识点节点

### 节点 1 · 布局抖动：量一次改一次（漫画第 1 格）

- **生活映射**：读一次尺寸改一次墙 = 循环里交替读写，每读一次 `offsetTop` 浏览器就被迫重排一次。
- **技术对应**：强制同步布局（Forced Synchronous Layout）；解法是批量读、批量写。
- **深入阅读**：📖 [3. 强制同步布局与布局抖动](../docs/04-rendering#_3-强制同步布局与布局抖动)

### 节点 2 · 成本阶梯：换窗帘不搬家（漫画第 2 格）

- **生活映射**：只刷漆不动家具 = 只重绘；换窗帘连房间都不用进 = 纯合成。
- **技术对应**：重排（width/top）最贵 > 重绘（color）> 合成（transform/opacity）最便宜；动画只该用后两者。
- **深入阅读**：📖 [2. 重排、重绘与合成的成本阶梯](../docs/04-rendering#_2-重排重绘与合成的成本阶梯)

### 节点 3 · 合成层：常改的东西单独放房（漫画第 3 格）

- **生活映射**：单独房间里的活不影响主屋 = 独立图层由 GPU 独立合成；但房间太多，电工（显存与合成器）跑断腿 = 层爆炸。
- **技术对应**：`will-change` 提升图层要克制——只给实测有瓶颈的频繁变化元素，用完移除。
- **深入阅读**：📖 [4. 合成层与 will-change](../docs/04-rendering#_4-合成层与-will-change)、[5. 主线程与长任务](../docs/04-rendering#_5-主线程与长任务)

### 节点 4 · 框架里的同类问题：没变就别重做（漫画第 4 格）

- **生活映射**：没变的菜端旧盘 = Vue `v-memo` / React `memo` 跳过未变化的渲染。
- **技术对应**：先测量确认无效重渲染热点，再精准缓存，不要全站乱包 memo。
- **深入阅读**：📖 [8. 框架落地：v-memo 与 React.memo](../docs/04-rendering#_8-框架落地v-memo-与-reactmemo)

## 常见认知误区

| 误区 | 真相 |
| --- | --- |
| 加上 will-change 就会变快 | 它只是提前创建图层的声明，滥用占显存反而更卡；先测量再加 |
| CSS 动画一定比 JS 动画快 | 用了 top/left 的 CSS 动画照样每帧重排；关键看属性层级 |
| 虚拟列表是万能的 | 它只解决 DOM 规模问题；行内布局抖动/重渲染该用读写分离与 v-memo |

## 自测三题

**1. 布局抖动（强制同步布局）的典型写法是？**

A. 先批量读、再批量写　B. 读-写-读-写交错执行　C. 用 transform 做动画

> 答案：B。读写交错会迫使浏览器反复同步计算布局。

**2. 渲染成本从低到高排序正确的是？**

A. 合成 < 重绘 < 重排　B. 重排 < 重绘 < 合成　C. 重绘 < 重排 < 合成

> 答案：A。重排代价最高，合成最低。

**3. 想只触发合成层动画，应修改哪个属性？**

A. width　B. top / left　C. transform / opacity

> 答案：C。transform 与 opacity 可只走合成阶段。

## 一句话带走

**读写分离、优先 transform 与 opacity、合成层省着用——让浏览器每帧只干最少的活。**
