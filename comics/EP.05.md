# EP.05 · 《仓库整理惊魂》

> 🎬 漫画：[EP.05.svg](./EP.05.svg) ｜ 📄 对应文档：[第 5 章 · 运行时性能：主线程、内存与泄漏](../docs/05-runtime.md)
>
> 本话主旨：主线程要会休息（切片/Worker），内存要舍得扔（清理泄漏）。

## 本话剧情

小奔的仓库陷入瘫痪：一个工人被超大件货物卡死，全部订单排队（长任务阻塞主线程）；稳叔盘点库存发现满墙「已作废订单」还挂着（游离 DOM、忘记清理的定时器）。治理方案：大活拆小份穿插着干（任务切片）、不要的东西及时贴丢弃标签清走（卸载时清理），实在搬不动的重活雇外包（Web Worker）。

## 知识点节点

### 节点 1 · 长任务：工人被大件卡住（漫画第 1 格）

- **生活映射**：工人搬一件 3 秒的大件期间，所有订单只能排队 = 主线程执行超 50ms 的任务期间无法响应任何输入。
- **技术对应**：事件循环里渲染发生在任务之间；超 50ms 即长任务，直接推高 INP。
- **深入阅读**：📖 [1. 事件循环：浏览器的时间切片法则](../docs/05-runtime.md#1-事件循环浏览器的时间切片法则)、[2. 长任务切分与调度](../docs/05-runtime.md#2-长任务切分与调度)

### 节点 2 · 内存泄漏：作废订单挂满墙（漫画第 2 格）

- **生活映射**：已作废的订单还挂在墙上占地方 = 已从页面删除的 DOM、已失效的定时器还被引用着，GC 永远不敢回收。
- **技术对应**：四大泄漏模式——意外全局、忘清定时器、游离 DOM、闭包持有大数据；堆快照对比是排查利器。
- **深入阅读**：📖 [4. 四大内存泄漏模式](../docs/05-runtime.md#4-四大内存泄漏模式)

### 节点 3 · 雇外包：Web Worker（漫画第 3 格）

- **生活映射**：搬不动的重活交给外包团队 = 与 DOM 无关的稳定重计算搬进 Worker 线程，主线程零阻塞。
- **技术对应**：Worker 不能操作 DOM；大数据用 Transferable 零拷贝传递；用完 terminate。
- **深入阅读**：📖 [5. Web Worker：把重活搬出主线程](../docs/05-runtime.md#5-web-worker把重活搬出主线程)

### 节点 4 · 最大坑点：闭包拽住整间仓库（漫画第 4 格）

- **误区**：闭包随手一包，只想用 `length` 却拽住了整个 10 万条数组——一个变量放不下一间仓库。
- **正解**：只捕获需要的值；框架组件里每个副作用都有销毁路径（Vue `onUnmounted` / React effect 清理函数）。
- **深入阅读**：📖 [3. V8 内存管理与垃圾回收](../docs/05-runtime.md#3-v8-内存管理与垃圾回收)、[7. 框架落地：组件卸载时的资源清理](../docs/05-runtime.md#7-框架落地组件卸载时的资源清理)

## 常见认知误区

| 误区 | 真相 |
| --- | --- |
| JS 有 GC 就不会内存泄漏 | GC 只回收不可达对象；只要还有引用挂着就永远回收不掉 |
| 切片越细越好 | 切片本身有调度开销，按 50ms 红线控制粒度即可 |
| setTimeout(fn, 0) 就是异步了 | 它仍占主线程执行时间；重计算要切片或上 Worker，不能只靠延迟 |

## 自测三题

**1. 长任务的判定阈值是多少？**

A. 16ms　B. 50ms　C. 100ms

> 答案：B。超过 50ms 的任务会阻塞输入响应，直接推高 INP。

**2. 下列哪种不属于典型内存泄漏？**

A. 忘记清理 setInterval　B. 闭包持有超大数组　C. 用 const 声明变量

> 答案：C。const 只是绑定不可变，与泄漏无关。

**3. 纯计算型重活应优先怎么处理？**

A. 拆成微任务　B. 放进 Web Worker　C. 用 requestAnimationFrame

> 答案：B。Worker 不占主线程；微任务与 rAF 仍在主线程执行。

## 一句话带走

**主线程要会休息（切片 + Worker），内存要舍得扔（及时清理引用）——卡顿与泄漏都是「不肯放手」造成的。**
