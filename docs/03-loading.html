1. 关键渲染路径：浏览器拿到 HTML 之后

浏览器渲染首屏的最短路径叫关键渲染路径（Critical Rendering Path）：

HTML ──解析──▶ DOM 树 ──┐
                        ├──▶ 渲染树 ──▶ Layout ──▶ Paint ──▶ 用户看到内容
CSS  ──解析──▶ CSSOM ──┘

两个会「堵路」的关键机制：

  1. CSS 阻塞渲染：浏览器要等所有 render-blocking CSS 下载并解析完才渲染首屏。首屏用不到的 CSS（主题、弹窗、打印样式）都在拖慢 FCP。
  2. JS 阻塞解析：默认的 <script src> 会阻塞 HTML 解析（要先下载执行完才继续）。

<script> 三种加载方式的差异（必须烂熟）：

方式 HTML 解析 执行时机 适用
<script src> ⛔ 阻塞 下载完立即执行 极少用（依赖顺序且必须早执行）
<script async src> 不阻塞 下载完立即执行（顺序不确定） 独立脚本：统计、广告
<script defer src> 不阻塞 DOM 解析完、DOMContentLoaded 前按序执行 应用主体脚本（默认选它）

关键 CSS 内联：首屏必需的样式（约 14KB 内）内联进 HTML，其余样式异步加载：

<!-- 文件: index.html 片段 —— 关键 CSS 内联 + 全量样式异步化 -->
<head>
  <style>/* 首屏关键样式：布局骨架、首屏组件，约 10~14KB */</style>
  <!-- 非关键 CSS 异步加载：不支持  preload 的浏览器回退 noscript -->
  <link rel="preload" href="/css/full.css" as="style" onload="this.rel='stylesheet'">
  <noscript><link rel="stylesheet" href="/css/full.css"></noscript>
</head>

运行方式：静态页面直接验证；Vite 项目可用 vite-plugin-critical 类插件自动化。

2. 网络层优化：CDN 与连接预热

CDN：把静态资源部署到离用户最近的边缘节点，缩短物理往返（RTT）。这是 TTFB 优化的第一杠杆，且几乎零成本——静态资源上 CDN 是底线要求。

HTTP/2 与 HTTP/3：HTTP/1.1 同一连接同时只能处理一个请求（队头阻塞），HTTP/2 多路复用让多个请求并行跑在一条连接上。这意味着：合并文件的「雪碧图/拼包」手法在 HTTP/2 下不再是必需，甚至有害（缓存粒度变差）。

连接预热：对关键第三方域提前建连，省下 100~300ms 的 DNS/TCP/TLS 握手：

<!-- 文件: index.html 片段 —— 资源提示：提前建连 -->
<link rel="preconnect" href="https://cdn.example.com">       <!-- DNS+TCP+TLS 全套，给最关键的域 -->
<link rel="dns-prefetch" href="https://analytics.example.com"> <!-- 只做 DNS，给次要的域 -->

运行方式：静态标签，打开 DevTools Network 面板观察连接 Timing 中 Waiting 阶段的变化。

优先级提示：对 LCP 主图加 fetchpriority="high"，让浏览器优先下载：

<img src="/hero.avif" fetchpriority="high" alt="首屏主图">

2.2 CDN 接入完整流程（以 Cloudflare 为例）

Cloudflare 免费版覆盖绝大多数个人/中小团队场景，且是少数不需要备案就能给国内用户加速的方案（走海外节点，延迟略高但仍优于直连源站）。

Step 1: 注册 Cloudflare 账号 → 点击「添加站点」→ 输入你的域名（如 static.example.com）
Step 2: 选择「免费计划」→ Cloudflare 自动扫描现有 DNS 记录
Step 3: 到域名注册商处，把 NS 服务器改成 Cloudflare 提供的两个（如 xxx.ns.cloudflare.com / yyy.ns.cloudflare.com）
Step 4: 等待 NS 生效（几分钟到几小时）→ Cloudflare 面板显示「已激活」
Step 5: 「SSL/TLS」→ 加密模式选「Full (strict)」（源站也必须有有效证书）；「边缘证书」开启自动 HTTPS
Step 6: 「网络」→ 开启 HTTP/3 (QUIC) 和 WebSocket
Step 7: 「缓存」→ 配置缓存规则（见下一节 2.3）
Step 8: DNS 面板添加 CNAME：`cdn → 你的源站域名` → 橙色云朵（代理状态，走 Cloudflare 边缘）
Step 9: 本地验证：`curl -I https://cdn.example.com/app.3f9a2b.js` 看 `CF-Cache-Status` 头

💡 关键概念：Cloudflare 的「橙色云朵」= DNS 解析走 Cloudflare 边缘 + 代理（加速/缓存/安全全部生效）；「灰色云朵」= 纯 DNS 解析（不代理，不走边缘）。静态资源子域名务必开橙云。

2.3 缓存规则配置（最容易错的环节）

CDN 接入成功只是开始，缓存规则决定了能节省多少回源带宽、降低多少 TTFB。错误的缓存规则轻则资源不更新，重则旧资源长期污染。

Edge Cache TTL：边缘节点缓存多久

Cloudflare 默认 4 小时，实际按资源类型分档：

带内容 hash 的静态资源（app.3f9a2b.js / hero.avif） → Edge TTL: 1 个月（30d）
  → 文件名变了就是新 URL，旧 URL 永远不需要刷新
HTML 文档（index.html / list.html） → Edge TTL: 1 小时
  → HTML 是「目录」，引用了带 hash 的资源；每次发版只需刷新 HTML
API 响应（/api/*） → Edge TTL: 不缓存（或 0s）
  → API 数据实时性优先，不走 CDN 缓存

配置方式（Cloudflare）：

规则 → 创建规则 → 匹配条件（例如 URI Path 包含 ".js"）→ 动作「设置缓存 TTL」→ 30d

Cache Key：缓存键设计

默认 Cache Key = URL 完整路径 + 查询参数。但一些场景需要定制：

场景 Cache Key 应该包含 说明
所有静态资源 去掉查询参数（忽略 ?v=xxx） 内容 hash 已在文件名里，查询参数是冗余的
按设备分流的资源 设备类型（desktop/mobile） /assets/layout.js?device=mobile 和 /assets/layout.js?device=desktop 应该是两份缓存
按语言分流 Accept-Language 头 ?lang=zh 和 ?lang=en 是不同内容
API 响应 全部包含（完整 URL + 查询参数） 不同参数就是不同数据

💡 内容寻址缓存（文件名带 hash）的最佳实践：Cache Key 去掉查询参数 + Edge TTL 设最长，构建时每次内容变更自动生成新文件名，CDN 自然命中新内容，永不需要手动刷新。第 7 节有更详细的缓存策略组合。

主动刷新：Purge 什么时候用

Purge 是「强制让边缘节点丢弃某个 URL 的缓存、下次回源重新拉」。只有两种场景需要手动 Purge：

  1. 发版时刷新 HTML 文档（如果 HTML 的 Edge TTL 设了 > 0）：curl -X PURGE https://cdn.example.com/index.html
  2. 紧急回滚/热修复：某个资源发现 bug 已覆盖，需要让缓存立即可用新内容

⚠️ 绝对不要 Purge 带内容 hash 的资源。app.3f9a2b.js 内容永远不会变——Purge 只会浪费边缘节点的缓存命中、白白增加回源带宽。如果真的要改内容，改完 hash 重新构建，新文件名就是新 URL。

Purge 方式：

# Cloudflare API 刷新单个 URL
curl -X POST "https://api.cloudflare.com/client/v4/zones/{zone_id}/purge_cache" \
  -H "Authorization: Bearer {api_token}" \
  -H "Content-Type: application/json" \
  -d '{"files": ["https://cdn.example.com/index.html"]}'

# 刷新标记（Purge Tag）：给一批资源打同一个 tag（如 "v2026.10.21"），按 tag 批量刷新
curl -X POST "https://api.cloudflare.com/client/v4/zones/{zone_id}/purge_cache" \
  -H "Authorization: Bearer {api_token}" \
  -H "Content-Type: application/json" \
  -d '{"tags": ["v2026.10.21"]}'

跨域配置：字体和图片的坑

CDN 域名和主站域名不同时，浏览器会把跨域资源视为 CORS 请求。字体文件是最常见的受害者——没有正确的 Access-Control-Allow-Origin，浏览器会直接拒绝加载（不报 404，字体就是不显示，调试时容易困惑）。

Cloudflare / Nginx 侧配置：

# 文件: nginx.conf 片段 —— CDN 回源 Nginx，给跨域资源加 CORS
location ~* \.(woff2?|ttf|otf|eot|js|css|avif|webp|png|jpg)$ {
    add_header Access-Control-Allow-Origin "https://example.com";
    add_header Cache-Control "public, max-age=31536000, immutable";
}

Cloudflare 面板路径：规则 → 修改响应头 → 添加 Access-Control-Allow-Origin: https://example.com。

2.4 构建流程集成：CI/CD 自动上传 + 刷新

手动上传 + 手动刷新是反模式。正确做法是 npm run build 之后 CI/CD 自动把产物推到 CDN 并触发刷新。

以 Cloudflare R2（对象存储，定价是 S3 的一半且无出站流量费）为例，GitHub Actions 工作流片段：

# 文件: .github/workflows/deploy-cdn.yml —— 构建 → 上传 R2 → 刷新 CDN
name: deploy-cdn
on:
  push:
    branches: [main]

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 22 }
      - run: npm ci && npm run build

      # ① 把 dist/ 产物上传到 Cloudflare R2（对象存储，作为 CDN 回源）
      - name: Upload to R2
        uses: cloudflare/pages-action@v1
        # 或用 aws s3 sync（R2 兼容 S3 API）
        # run: aws s3 sync dist/ s3://my-cdn-bucket/ --endpoint-url ${{ secrets.R2_ENDPOINT }}

      # ② 刷新 CDN 上 HTML 文档的缓存（静态资源带 hash，永远不 Purge）
      - name: Purge HTML cache
        run: |
          curl -X POST "https://api.cloudflare.com/client/v4/zones/${{ secrets.CF_ZONE_ID }}/purge_cache" \
            -H "Authorization: Bearer ${{ secrets.CF_API_TOKEN }}" \
            -H "Content-Type: application/json" \
            -d '{"files": ["https://cdn.example.com/index.html"]}'

运行方式：把 CF_ZONE_ID 和 CF_API_TOKEN（需有 Zone > Cache > Purge 权限）存到 GitHub Repo Secrets；推 main 分支自动触发。CF_API_TOKEN 在 Cloudflare → 「我的资料」→「API Tokens」创建，不要用 Global API Key。

关键设计：静态资源（带 hash）永远不 Purge——它们通过文件名变更自然更新。只有 HTML 文档（引用了新 hash 的资源）需要刷新。这一个设计就能让 CDN 命中率从 60% 提升到 95%+。

国内阿里云 OSS + CDN 的流程完全类似：用 ossutil cp -r dist/ oss://my-bucket/ 上传 → 调用阿里云 CDN API 刷新 URL。腾讯云用 coscmd upload + CDN 刷新 API。

2.5 效果验证：怎么确认 CDN 真的在工作

接好 CDN 后必须验证，否则可能「以为在加速，实际上直连源站」。三步验证法：

① 命令行看响应头

# -I 只看头，关键头如下
curl -I https://cdn.example.com/app.3f9a2b.js

# Cloudflare CDN 的典型响应头：
# CF-Cache-Status: HIT        ← 边缘节点命中（MISS = 回源了，检查缓存规则）
# CF-Ray: 8abc123...-SJC      ← 最后一段是边缘节点位置（SJC=圣何塞）
# Server: cloudflare          ← 确认走了 Cloudflare 而非直连源站
# Age: 86400                  ← 该资源在边缘已缓存 1 天（秒）

如果 CF-Cache-Status: MISS 持续出现，检查：缓存规则是否覆盖了该路径？回源 Nginx 的 Cache-Control 头是否正确？Purge 是否刚刚执行过（Purge 后第一次请求必然 MISS）？

② Lighthouse / DevTools 地理模拟

CDN 的核心价值是离用户近。在 DevTools Performance 面板或 Lighthouse 里模拟不同地理位置的用户：

# Lighthouse CLI 模拟东京用户测 TTFB
npx lighthouse https://example.com \
  --preset=perf \
  --chrome-flags="--proxy-server=socks5://localhost:1080 --host-resolver-rules='MAP * 0.0.0.0, EXCLUDE localhost'" \
  --only-audits=server-response-time

或者用 WebPageTest（webpagetest.org）选多个真实城市同时测——CDN 生效时，各地 TTFB 应该都在 200ms 以内（之前直连源站时可能有 500ms+）。

③ Cloudflare Analytics 面板

Cloudflare 提供实时面板：

  • 缓存命中率：目标 ≥ 95%（低于 80% 说明缓存规则有问题）
  • 总回源带宽：持续下降才对（缓存命中越多，回源越少）
  • 边缘节点分布：看请求是不是真的分发到了全球各地

💡 典型收益曲线：接 CDN 前 TTFB 在 4001200ms 波动（取决于用户到源站的物理距离）；接 CDN 后全球用户 TTFB 稳定在 80200ms，降低幅度是数量级的。这是单步优化里投资回报率最高的动作。

3. 资源压缩与传输

文本类资源（JS/CSS/HTML/SVG/JSON）必须压缩，两档压缩对比：

算法 压缩率 CPU 成本 兼容性
gzip 基准 低 全量
Brotli 比 gzip 再小 15~20% 压缩高/解压低 全部现代浏览器

实践组合拳：

  1. 构建期预压缩：产物同时产出 .gz 与 .br 文件（vite-plugin-compression2 等），Nginx 直接发预压缩文件，避免请求时实时压缩的 CPU 开销；
  2. minify 必开：Terser/esbuild 压缩 JS、cssnano 压 CSS；
  3. 图片/视频/WOFF2 不再 gzip：本身已是压缩格式，二次压缩白白耗 CPU；
  4. 开启 HTTP/2：Nginx listen 443 ssl http2;。

4. 图片优化：格式、响应式与懒加载

图片通常占页面流量的大头，是加载优化的最大单项收益来源。

格式选型：WebP 比 JPEG 小 25~35%，AVIF 再小 20% 左右；新格式用 <picture> 兜底：

<!-- 文件: 图片响应式与格式降级模板 -->
<picture>
  <source type="image/avif" srcset="hero.avif">
  <source type="image/webp" srcset="hero.webp">
  <img src="hero.jpg" alt="首屏主图" width="1200" height="600"
       fetchpriority="high"><!-- width/height 防止 CLS -->
</picture>

<!-- srcset/sizes：按视口宽度发合适尺寸，避免手机下载 3x 大图 -->
<img srcset="photo-400.jpg 400w, photo-800.jpg 800w, photo-1600.jpg 1600w"
     sizes="(max-width: 600px) 400px, 800px"
     src="photo-800.jpg" alt="正文配图" loading="lazy" decoding="async">

运行方式：静态页面直接验证；用 DevTools Network 面板按设备模拟确认实际命中的资源。

懒加载的正确姿势：

  • 原生优先：loading="lazy"（Chrome 77+ 全量支持）；
  • 复杂场景（滚动容器内/动画触发）用 IntersectionObserver 手动控制；
  • 铁律：LCP 元素（首屏主图）绝不懒加载——懒加载会推迟它的发现时机，直接拖慢 LCP。
// 文件: 示例片段 —— IntersectionObserver 懒加载（原生 loading 不够用的场景）
const io = new IntersectionObserver((entries) => {
  for (const e of entries) {
    if (!e.isIntersecting) continue;
    const img = e.target;
    img.src = img.dataset.src;        // 进入视口再发真实请求
    io.unobserve(img);                // 加载一次即停，避免重复回调
  }
}, { rootMargin: '600px 0px' });      // 提前 600px 预取，滚动到时刚好加载完
document.querySelectorAll('img[data-src]').forEach((img) => io.observe(img));

运行方式：浏览器打开含 data-src 图片的页面，在 Network 面板观察按需加载时序。

5. 字体加载策略

Web 字体是隐性杀手：字体文件常达 200KB+，且默认会阻塞文本渲染（隐形文本闪烁 FOIT）。

四步标准方案：

<!-- 文件: index.html 片段 —— 字体加载四件套 -->
<link rel="preload" href="/fonts/main.woff2" as="font" type="font/woff2" crossorigin>
<style>
  @font-face {
    font-family: 'Main';
    src: url('/fonts/main.woff2') format('woff2'); /* 只用 WOFF2，现代浏览器全覆盖 */
    font-display: swap;  /* 下载期先用回退字体显示，避免白屏 */
    size-adjust: 98%;    /* 微调回退字体度量，减少换行抖动（防 CLS） */
  }
</style>
font-display 行为 适用
auto/block 等字体（最长约 3s 隐形文本） 默认，不建议
swap 立即用回退字体，字体到了再换 大多数场景（可能闪一下）
optional 100ms 内没下完就整周期用回退字体 强稳定性诉求（CLS 最优）

进阶：子集化（fonttools/glyphhanger 只保留用到的字符，中文场景收益巨大，几百 KB 可压到几十 KB）。

6. JavaScript 交付与代码分割

JS 是首屏最常见的负担。优化三板斧：

① Tree Shaking：确保 package.json 标注 "sideEffects": false（或列出有副作用的文件），让打包器安全删除未引用代码；工具库按子路径引入（import debounce from 'lodash-es/debounce'）。

② 代码分割：按「路由级 → 重组件级」两级拆分，首屏只加载首屏需要的代码：

// 文件: src/router.js 片段 —— 动态 import 实现路由级分割（Vue 与 React 通用）
const routes = [
  // 首页同步加载（保证首屏最快）；其余页面按需加载
  { path: '/', component: () => import('./views/Home.vue') },
  { path: '/admin', component: () => import('./views/Admin.vue') }, // 管理后台不在首包
];

③ 产物瘦身验证：用 rollup-plugin-visualizer（Vite）或 webpack-bundle-analyzer 看包构成，重点排查重复依赖与误整包引入。

7. 缓存策略设计

HTTP 缓存两层机制：

机制 关键头 行为
强缓存 Cache-Control: max-age=31536000 有效期内浏览器不发请求，直接用本地副本
协商缓存 ETag / Last-Modified 发请求问服务器「变了没」，没变返回 304

标准组合（内容寻址缓存）：

带内容 hash 的静态资源：Cache-Control: public, max-age=31536000, immutable
  → app.3f9a2b.js 内容变了文件名就变，缓存永不冲突，可以放心缓存一年
HTML 文档：            Cache-Control: no-cache
  → 每次协商校验，保证用户总能拿到引用最新资源的 HTML

💡 一句话：HTML 不缓存（或短缓存），带 hash 的静态资源永久缓存。这一条做好，回访用户的 LCP 可以直接从网络级降到本地级。

8. 框架落地：路由分割与资源提示

框架项目里，代码分割通常已被脚手架默认支持，要做的是「确认分割粒度」与「补预热」：

Vue 3（Vite 脚手架默认动态 import 路由即自动分割）：

// 文件: src/router/index.js —— Vue Router 懒加载 + webpack 魔法注释命名分包
const routes = [
  {
    path: '/report',
    // 同一 chunk 的资源合并下载，便于缓存与并行
    component: () => import(/* webpackChunkName: "report" */ '../views/Report.vue'),
  },
];

React（React.lazy 必须配合 Suspense）：

// 文件: src/App.jsx —— React 路由级分割
import { lazy, Suspense } from 'react';
const Admin = lazy(() => import('./views/Admin'));

export default function App() {
  return (
    <Suspense fallback={<div>加载中…</div>}>
      <Admin />
    </Suspense>
  );
}

资源预热：对「用户大概率会去的下一个路由」提前拉取，点进去时零等待：

<!-- 文件: index.html 片段 —— 预取下一路由（空闲时拉取，不抢首屏带宽） -->
<link rel="prefetch" href="/assets/Admin-9f2c1a.js">

运行方式：npm run build 后观察 dist 产物目录的分包结构，DevTools Network 中确认 prefetch 在空闲期触发。

9. 最佳实践清单

  • 所有 <script> 默认 defer，独立第三方脚本才用 async
  • 关键 CSS 内联，全量 CSS 异步加载
  • 静态资源全部上 CDN，Brotli 预压缩产物
  • 图片：AVIF/WebP + srcset + 显式宽高；LCP 主图 fetchpriority="high" 且绝不懒加载
  • 字体：WOFF2 + preload + font-display: swap，中文大字体做子集化
  • Tree Shaking 生效（sideEffects 配置正确），路由级代码分割到位
  • 缓存：hash 资源 max-age=31536000, immutable，HTML no-cache
  • 对关键第三方域 preconnect，对下一路由 prefetch
