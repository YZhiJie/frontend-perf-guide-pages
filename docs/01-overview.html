第 1 章 · 性能优化总览与心智模型 ​

1. 为什么性能就是钱 ​

性能不是技术自嗨，而是直接的业务指标。几组被反复引用的研究结论：

研究结论数据来源含义
移动端加载时间从 1s 增加到 3s，跳出概率增加约 32%Google/SOASTA 2017等待时间与流失率强相关
加载时间快 0.1s，零售转化率提升约 8.4%，平均订单价值提升约 9.2%Deloitte/Google 2020毫秒级优化也有真实收益
Core Web Vitals 是 Google 搜索排名信号之一Google 官方性能影响 SEO 流量

三个关键认知：

  1. 用户没有耐心：移动端用户对超过 3 秒的加载容忍度极低，且一旦流失很难回来。
  2. 性能影响全漏斗：从首屏到达（SEO/跳出）到交互转化（下单/注册）到留存回访，每一环都有性能的身影。
  3. 性能是复利：0.1s 的优化看似微小，但对所有用户、所有请求都生效，长期累积收益巨大。

💡 一句话：性能优化的终极目标不是「分数好看」，而是「用户更快到达、更快操作、更愿意留下」。

2. 一条请求的旅程全景图 ​

用户输入 URL 到看到可交互页面，数据要经过一条长链路。性能问题可能出在每一环，这也是本教程的章节骨架：

text
[用户输入 URL]
    │
    ├─ ① 网络传输：DNS → TCP → TLS → HTTP 请求          （第 3 章 加载性能）
    │
    ├─ ② 服务器响应：TTFB 首字节时间（CDN/缓存/服务端）   （第 3 章 加载性能）
    │
    ├─ ③ 资源加载：HTML/CSS/JS/图片/字体下载与解析        （第 3 章 加载性能）
    │
    ├─ ④ 渲染管线：DOM/CSSOM → Style → Layout → Paint    （第 4 章 渲染性能）
    │    → Composite，主页面内容出现（LCP）
    │
    ├─ ⑤ 交互响应：事件 → JS 执行 → 下一帧渲染（INP）     （第 5 章 运行时性能）
    │
    └─ ⑥ 框架运行时：组件树更新、状态管理、虚拟 DOM       （第 6/7 章 Vue/React 专项）

对应的核心指标（第 2 章详解）：

  • TTFB：链路 ①② 的健康度
  • FCP / LCP：链路 ③④ 的健康度（用户「看到内容」）
  • INP：链路 ⑤⑥ 的健康度（用户「操作有反馈」）
  • CLS：链路 ④ 的视觉稳定性副产品

全景图的作用：收到「页面慢」的报告时，先按这张图定位慢在哪一环，而不是上来就改代码。

3. RAIL 模型四刻度 ​

RAIL 是 Google 提出的以用户为中心的性能模型，回答「多快才算快」：

字母含义目标用户感受边界
Response响应输入后 100ms 内给出反馈超过 100ms 感觉「迟钝」
Animation动画每帧 16ms 内完成（60fps）掉帧感到「卡顿」
Idle空闲主线程任务切 50ms 以内的块长任务阻塞后续交互
Load加载1s 内呈现关键内容超过 1s 注意力游离

实践要点：

  • 100ms 的响应预算里，真正的处理时间只有约 50~70ms（要给浏览器留出渲染下一帧的时间），所以长任务必须切片。
  • 16ms 一帧不是要求 JS 执行只花 16ms，而是「JS + 样式 + 布局 + 绘制 + 合成」的总和在一帧内完成。
  • Load 的 1s 指「关键内容可见」，不等于「全部资源加载完毕」——这正是「关键渲染路径」优化的意义（第 3 章）。

4. 度量先行的优化方法论 ​

性能优化的标准工作流是一个闭环，顺序不能乱：

text
┌──────────────────────────────────────────────────────┐
│  ① 度量建立基线                                        │
│     实验室：Lighthouse / DevTools Performance          │
│     真实用户：web-vitals 上报 + RUM 看板                │
├──────────────────────────────────────────────────────┤
│  ② 定位瓶颈                                            │
│     Network 瀑布图找慢资源                              │
│     Performance 火焰图找长任务与布局抖动                 │
├──────────────────────────────────────────────────────┤
│  ③ 单点优化                                            │
│     一次只改一类问题（如只做图片优化）                    │
│     改动越小，归因越清晰                                 │
├──────────────────────────────────────────────────────┤
│  ④ 复测验证                                            │
│     同一环境同一方法复测，与基线对比                      │
│     有效 → 沉淀成规范；无效 → 回滚并换方向               │
└──────────────────────────────────────────────────────┘
          ↑______________________________________│

三条铁律：

  1. 没有基线就没有优化：改之前先跑一次完整测量并记录数据，否则无法证明优化有效。
  2. 一次只改一处：同时改五个地方，性能变好了不知道谁的功劳，变差了不知道谁的锅。
  3. 区分实验室数据与真实数据：实验室（Lighthouse）用于定位问题，真实用户数据（RUM）用于下业务结论。
js
// 文件: 示例片段（完整可运行版本见 examples/05-web-vitals-demo.html）
// 用 PerformanceObserver 在真实用户环境采集 LCP——度量先行的第一步
new PerformanceObserver((list) => {
  const entries = list.getEntries();
  const last = entries[entries.length - 1]; // LCP 候选元素会随加载更新，取最后一个
  console.log('LCP:', last.startTime, '元素:', last.element);
}).observe({ type: 'largest-contentful-paint', buffered: true });

运行方式：将片段嵌入任意页面打开 DevTools Console 即可看到输出；完整示例见 examples/05-web-vitals-demo.html。

5. 性能预算给项目立规矩 ​

性能预算（Performance Budget）是把「多快才算快」翻译成可执行、可校验的硬性约束。没有预算的团队，性能会在迭代中无声劣化（第 9 章讲如何用 CI 强制执行）。

一份可直接套用的预算模板：

预算项建议阈值校验工具
JS 总量（压缩后）≤ 170KBsize-limit / bundlesize
关键 CSS≤ 14KB（首屏内联）构建脚本统计
LCP（75 分位真实用户）≤ 2.5sRUM 看板
INP（75 分位真实用户）≤ 200msRUM 看板
CLS（75 分位真实用户）≤ 0.1RUM 看板
Lighthouse 性能分≥ 85（CI 环境）Lighthouse CI
请求总数（首屏）≤ 50DevTools Network

制定预算的原则：

  1. 少数关键项：预算项控制在 5~8 个，多了没人看。
  2. 绑定 CI 而非口头：超标就拦，而不是「下次注意」。
  3. 随业务调整：大促页面可以单独立预算，不与日常页混用。

6. Vue 与 React 从哪下手 ​

框架项目的性能问题高度集中在两个环节：加载（包体积） 与 运行时（无效重渲染）。本教程的框架专项章节（第 6、7 章）展开细节，这里先给优先级地图：

优先级问题Vue 对应方案React 对应方案
P0首屏包体积过大路由级 import() 分割、组件库按需引入React.lazy + Suspense
P0首屏资源未优化与框架无关：图片/字体/压缩（第 3 章）同左
P1列表更新卡顿v-memo、虚拟滚动memo + 虚拟列表
P1大对象深层响应式开销shallowRef / markRaw不可变数据结构选型
P2交互长任务任务切片 + nextTick 调度useTransition / useDeferredValue
P2内存泄漏卸载时清理副作用（onUnmounted）清理 useEffect 返回函数

💡 框架优化的大原则：先解决「加载了多少」，再解决「渲染了多少」。包体积问题是确定性的（数字摆在那），重渲染问题需要先测量再动手。

7. 最佳实践清单 ​

  • [ ] 每个性能优化立项前，先建立基线数据（实验室 + 真实用户两套）
  • [ ] 用 RAIL 刻度校准团队对「快」的共识：响应 100ms、动画 16ms、空闲 50ms、加载 1s
  • [ ] 为项目制定 5~8 项性能预算并写入 CI 门禁
  • [ ] 收到「页面慢」先按请求旅程六环节定位，不盲目改代码
  • [ ] 框架项目按 P0（加载）→ P1（重渲染）→ P2（调度）顺序推进
  • [ ] 每次优化只改一类问题，改完复测对比基线
  • [ ] 优化结论沉淀为团队规范，避免同一个坑踩第二次
