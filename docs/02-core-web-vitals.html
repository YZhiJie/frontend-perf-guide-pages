1. 指标全景与评分标准

Core Web Vitals（2024 年 3 月起，INP 取代 FID 成为核心三指标之一）+ 两个诊断性指标：

指标 全称 测量什么 好 需改进 差 性质
LCP Largest Contentful Paint 最大内容元素渲染时间 ≤ 2.5s ≤ 4.0s > 4.0s 核心
INP Interaction to Next Paint 最差交互的响应延迟 ≤ 200ms ≤ 500ms > 500ms 核心
CLS Cumulative Layout Shift 累计布局偏移 ≤ 0.1 ≤ 0.25 > 0.25 核心
TTFB Time to First Byte 首字节到达时间 ≤ 0.8s ≤ 1.8s > 1.8s 诊断
FCP First Contentful Paint 首次内容渲染 ≤ 1.8s ≤ 3.0s > 3.0s 诊断

三个关键口径，理解错会全盘跑偏：

  1. 分位口径：评分看的是真实用户数据的 75 分位（p75），不是实验室单次跑分。
  2. 实验室 vs 真实：Lighthouse 是实验室工具（模拟环境），只能用于定位问题；下业务结论必须用真实用户数据（field data）。
  3. 指标是结果不是原因：LCP 慢可能是网络、资源、渲染任何一环的问题，要配合诊断指标溯源（见第 8 章工具）。

2. TTFB：第一字节的等待

定义：从发起请求到收到响应第一个字节的时间，覆盖 重定向 → DNS → TCP → TLS → 请求 → 服务端处理 → 首字节回程。

// 用 Resource Timing 读 HTML 文档的 TTFB
const [entry] = performance.getEntriesByType('navigation');
console.log('TTFB:', entry.responseStart, 'ms');
// 各阶段拆解：重定向/ DNS / TCP / TLS 耗时
console.log('DNS:', entry.domainLookupEnd - entry.domainLookupStart);
console.log('TCP:', entry.connectEnd - entry.connectStart);
console.log('TLS:', entry.requestStart - entry.secureConnectionStart);

优化手段（按收益排序）：

  1. CDN：静态资源与 SSR 页面边缘缓存，缩短物理距离；
  2. 强缓存命中：带 hash 的资源直接从本地/边缘返回（第 3 章第 7 节）；
  3. 提前建连：<link rel="preconnect"> 提前完成 DNS/TCP/TLS；
  4. 服务端瘦身：SSR 渲染耗时、慢 SQL、无谓重定向链（http → https → www 每一跳都计入）。

3. FCP：第一印象

定义：页面首次渲染出任何文本、图片、SVG 或 canvas 的时间。它回答「用户是不是觉得页面动起来了」。

优化手段：与 LCP 高度重合——减少阻塞渲染的 CSS/JS、关键 CSS 内联、字体用 font-display: swap（见第 3 章）。FCP 快但 LCP 慢，说明「壳先出来了、主内容卡住」，通常是主图/首屏数据请求慢。

4. LCP：最大内容元素何时出现

定义：视口内最大的图片或文本块渲染完成的时间。注意是「最大的元素」而非「最后加载的元素」。

LCP 候选元素只有五类：<img>、内嵌 <image> 的 SVG、带 poster 的 <video>、CSS background-image 元素、块级文本容器（<p>/<h1>/<div> 整段文本）。

// LCP 测量：候选元素会随加载不断更新，取最后一个即为最终 LCP
new PerformanceObserver((list) => {
  const entries = list.getEntries();
  const last = entries[entries.length - 1];
  console.log('LCP:', last.startTime, 'ms，元素:', last.element, 'URL:', last.url);
}).observe({ type: 'largest-contentful-paint', buffered: true });
// 注意：用户首次交互后 LCP 停止更新（交互说明用户已在看内容）

四大优化方向：

方向 手段 章节
服务端出字节更快 CDN、缓存、preconnect 第 3 章 2/7/8 节
资源本身更小 主图用 WebP/AVIF、srcset 响应式、首图 fetchpriority="high" 第 3 章 3/4 节
更早被发现 首屏图 <link rel="preload" as="image">，别把首屏图塞进懒加载 第 3 章 4/8 节
渲染不被阻塞 CSS 精简、JS defer、关键 CSS 内联 第 3 章 1/6 节

高频反例：把轮播首图/懒加载逻辑错用在 LCP 元素上（loading="lazy" 会让首图变慢）；LCP 是 <h1> 文本却用自定义字体且无 font-display，字体下载阻塞文本渲染。

5. INP：交互响应的灵魂拷问

定义：整次页面访问中最差的一次交互（点击/触摸/键盘）从输入到下一帧渲染完成的延迟；真实数据取 p98 以剔除离群值。

一次交互延迟 = 输入延迟（主线程忙，事件排队）+ 处理时间（事件回调执行）+ 呈现延迟（下一帧渲染）。

// INP 的原始测量较复杂（需跟踪每次交互的最差延迟），
// 生产环境直接用 web-vitals 库（见本章第 7 节）；调试用 Chrome DevTools 事件轨道。

优化手段（对应三个延迟段）：

  1. 输入延迟：拆长任务，让主线程随时可响应（第 5 章第 2 节）；
  2. 处理时间：事件回调里只做同步必要工作，重活（排序、过滤、渲染大列表）延后；
  3. 呈现延迟：减少 DOM 规模、避免回调里触发大面积同步重排（第 4 章）。
// 文件: 示例片段 —— 长任务切片，避免输入延迟（浏览器调度器 API）
async function heavyWork(items) {
  for (const item of items) {
    process(item);
    // 每处理完一项让出主线程；不支持的浏览器回退 setTimeout
    if ('scheduler' in window && 'yield' in scheduler) {
      await scheduler.yield();
    } else {
      await new Promise((r) => setTimeout(r, 0));
    }
  }
}

运行方式：浏览器环境运行；scheduler.yield() 需要 Chrome 129+，代码含能力检测回退。

6. CLS：布局偏移的元凶排查

定义：整个生命周期内每次「意外布局偏移」得分的累计。单次偏移得分 = 影响比例（移动面积占视口比例）× 距离比例（移动距离占视口比例）。

// CLS 测量：只累计「非用户输入引发」的偏移
let cls = 0;
new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    if (!entry.hadRecentInput) cls += entry.value; // 输入后 500ms 内的偏移不计入
  }
  console.log('CLS:', cls);
}).observe({ type: 'layout-shift', buffered: true });

五大元凶与修复：

元凶 修复
图片/视频未声明尺寸 写死 width/height 或 CSS aspect-ratio，让浏览器提前占位
广告/嵌入内容动态注入 容器预先定高定宽，占位符兜底
动态插入内容挤开已有内容 预留空间，或插入到视口外/已有内容下方
Web 字体替换（FOUT） font-display: optional 或 size-adjust 匹配度量
动画用了 layout 属性 只动画 transform/opacity（第 4 章第 2 节）

7. 用 web-vitals 库采集真实用户数据

生产环境不要手写指标测量（INP 原始测量很复杂），用 Google 官方 web-vitals 库（约 1KB）：

npm install web-vitals

// 文件: src/perf-report.js —— 三大指标采集与上报（生产可用）
import { onLCP, onINP, onCLS, onTTFB, onFCP } from 'web-vitals';

function report(metric) {
  // 用 sendBeacon 在页面卸载时也能可靠送达；降级用 fetch keepalive
  const payload = JSON.stringify({
    name: metric.name,       // 'LCP' | 'INP' | 'CLS' | ...
    value: metric.value,
    id: metric.id,           // 用于后端按会话聚合
    rating: metric.rating,   // 'good' | 'needs-improvement' | 'poor'
    path: location.pathname,
  });
  if (navigator.sendBeacon) {
    navigator.sendBeacon('/api/perf', payload);
  } else {
    fetch('/api/perf', { method: 'POST', body: payload, keepalive: true });
  }
}

onLCP(report);
onINP(report);
onCLS(report);
onTTFB(report);
onFCP(report);

运行方式：npm i web-vitals 后在应用入口引入；本地调试可先把 payload 打印到 console。

进阶：import { onLCP } from 'web-vitals/attribution' 可拿到归因信息（LCP 是哪个元素/哪个阶段慢、CLS 是谁挪了谁），直接缩短定位路径。

8. 最佳实践清单

  • 团队对齐口径：所有指标讨论默认指真实用户数据 p75
  • 上线 web-vitals 采集 + 上报，后端按 metric.id 会话聚合出 p75
  • LCP 优化四查：CDN、图片格式与优先级、preload、渲染阻塞
  • INP 优化三查：长任务、回调里的大计算、DOM 规模
  • CLS 优化五查：媒体尺寸、占位、插入位置、字体策略、动画属性
  • FID 已废弃，老代码里对 FID 的监控迁移到 INP
  • 每个指标给出「好/需改进/差」三档的目标与告警线
