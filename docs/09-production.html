1. 性能预算的制定与强制执行

预算是落地流程的「宪法」——先立预算，再做优化，否则优化成果守不住。第 1 章第 5 节给出了模板，这里补上强制执行的工具链：

// 文件: package.json 片段 —— size-limit：产物体积预算，超标即 CI 失败
{
  "scripts": {
    "size": "size-limit"
  },
  "size-limit": [
    { "name": "首屏 JS", "path": "dist/assets/index-*.js", "limit": "170 KB" },
    { "name": "首屏 CSS", "path": "dist/assets/index-*.css", "limit": "40 KB" },
    { "name": "全站 JS", "path": "dist/assets/*.js", "limit": "500 KB", "gzip": false }
  ]
}

运行方式：npm i -D size-limit 后执行 npm run size；gzip: false 时按 Brotli/原始体积口径统计，注意与预算口径一致。

预算落地的三个层次（由弱到强）：文档约定 → 本地脚本 → CI 拦截。只有第三层真正有效。

2. 第一步：建立性能基线

优化前必须拿到「现状快照」，否则后面全是感觉流。基线包含三份数据：

# 文件: scripts/baseline.sh —— 基线采集脚本（多页面 × 多次运行取中位）
PAGES=("/" "/list" "/detail/1" "/login")
for p in "${PAGES[@]}"; do
  for i in 1 2 3; do
    npx lighthouse "https://example.com$p" \
      --preset=perf --output=json --output-path="./baseline/$(echo $p | tr '/' '_')-$i.json" \
      --chrome-flags="--headless"
  done
done
# 再用 jq 汇总各页面的 LCP/TBT/CLS 中位数，填入基线表

基线表模板：

页面 LCP p75 INP p75 CLS p75 JS 体积 Lighthouse 分 采集日期
/ 3.8s 340ms 0.21 420KB 62 2026-10-18

同时：DevTools 录一次典型用户操作的 Performance 存档、Network 导出 HAR——这些是后面每一步优化的对照组。

3. 第二步：一轮完整优化的标准流程

从指标倒推出工作清单，按「收益/成本比」排序执行：

指标劣化 ─▶ 定位链路 ─▶ 对应优化手段（章节索引）
─────────────────────────────────────────────
LCP 慢  ─▶ 加载链路  ─▶ CDN/缓存(第3章7) → 图片(第3章4) → 关键CSS(第3章1) → 预热(第3章2/8)
TBT/INP 高 ─▶ 主线程 ─▶ 切片(第5章2) → Worker(第5章5) → 框架重渲染(第6/7章)
CLS 大  ─▶ 视觉稳定 ─▶ 尺寸占位(第2章6) → 字体策略(第3章5) → 动画属性(第4章2)
包体积大 ─▶ 交付层  ─▶ 分割(第3章6/8) → 按需引入(第6章5) → 压缩(第3章3)

单轮优化的六步循环（一轮只解决一类问题）：

  1. 从基线表挑出最差的一个指标；
  2. 用第 8 章工具定位到具体环节与资源；
  3. 实施对应优化（按上表索引到具体章节手段）；
  4. 同环境复测，与基线对比，记录该措施的收益；
  5. 有效 → 固化为规范；无效 → 回滚，换下一候选；
  6. 更新基线表，进入下一指标。

4. 第三步：CI 门禁与回归防护

优化的敌人是「下个迭代悄悄劣化回去」。CI 门禁三件套（体积、分数、指标断言）：

# 文件: .github/workflows/perf-gate.yml —— 性能门禁：体积预算 + Lighthouse CI
name: perf-gate
on: [pull_request]
jobs:
  gate:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 22 }
      - run: npm ci
      - run: npm run build
      - name: 体积预算检查
        run: npx size-limit
      - name: Lighthouse 断言
        run: npx @lhci/cli autorun   # 断言配置见第 8 章第 3 节 lighthouserc.js

运行方式：PR 触发，任一门禁失败即拦截合并。阈值与第 1 章第 5 节的性能预算保持一致。

两条实战经验：门禁阈值设为「当前值 + 5% 容差」起步（太严会被绕过或长期红着），随优化逐步收紧；门禁失败的信息要能指导修复（size-limit/lhci 的输出直接给出超标明细）。

5. 第四步：RUM 监控上线与告警

CI 门禁守实验室口径，RUM 守真实用户口径（采集代码见第 2 章第 7 节）。上线三步：

  1. 后端聚合：按 metric.id（会话）+ 路由 + 设备分片，各指标算 p75/p98，按天落表；
  2. 看板：三大指标趋势 + 分路由热力（哪条路由最差）+ 与发版时间线对齐；
  3. 告警：p75 环比劣化超 10% 连续两天 → 触发告警并自动关联当次发版 diff。

发版后的标准动作：灰度对比——新版本对 10% 用户放量，对比新旧版本的 RUM 指标，确认优化真实生效后再全量。这一步是「实验室收益」与「业务收益」之间的验收关卡。

6. 优化实录：一个完整案例的前后对比

某电商首页（Vue 3，日均 PV 50 万）的一轮完整落地，供校准预期：

措施 对应章节 前后变化（该措施单项贡献）
LCP 主图换 AVIF + fetchpriority="high" + preload 第 3 章 4 LCP 3.8s → 2.9s
静态资源 Brotli + CDN 边缘缓存 第 3 章 3/7 TTFB 1.1s → 0.4s
关键 CSS 内联 + 全量样式异步 第 3 章 1 FCP 2.6s → 1.9s
路由/重组件分割，JS 420KB → 168KB 第 3 章 6 TBT 620ms → 240ms
首页长列表虚拟滚动 + v-memo 第 6 章 2/3 INP 340ms → 180ms
媒体显式宽高 + 字体 size-adjust 第 2 章 6 CLS 0.21 → 0.06
CI 门禁 + RUM 看板 本章 4/5 （防回归，无直接指标）

总计：LCP 3.8s→2.3s（-39%）、INP 340ms→180ms（-47%）、CLS 0.21→0.06（-71%）；上线后两周转化率提升约 6%。两点启示：单项措施都不惊艳，组合拳才出量级收益；RUM 验证是整个流程闭环的最后一环。

7. 团队协作：让性能成为日常

机制比热情可靠。四个可复制的制度：

  1. PR 性能清单：改动涉及首屏/列表/大依赖时，必须附性能自测说明（截图或数据）；
  2. 性能轮值：每周一人盯 RUM 看板与告警，发现劣化当天定位、当天提 issue；
  3. 新页面准入：新页面上线前跑基线脚本，指标不达预算不准放量；
  4. 复盘沉淀：每次优化案例（措施、数据、坑）沉淀进团队文档，与本教程各章建立索引。

8. 落地检查清单

按 0 → 1 顺序执行，全部完成即形成闭环体系：

  • 与业务方对齐目标，签下性能预算（第 1 章第 5 节模板）
  • 跑基线脚本，填基线表，DevTools/HAR 归档
  • 按六步循环完成首轮优化（收益最大的指标先行）
  • size-limit 体积预算进 package.json
  • Lighthouse CI（lighthouserc.js）+ GitHub Actions 门禁拦截 PR
  • web-vitals 采集上报上线，后端聚合 p75
  • RUM 看板 + 环比告警搭建完成
  • 发版流程加入灰度对比验收
  • PR 性能清单、轮值制度、新页面准入三制度落地
