第 10 章 · 企业级性能优化专题：白屏、GPU 与卡顿治理 ​

学习目标：掌握三大企业级高频顽疾的系统治理方案——白屏的根因分类与度量、GPU 加速的深入原理与边界、卡顿的线上监控与归因闭环。 前置知识：第 2 章（指标）、第 3 章（加载）、第 4 章（渲染管线与合成层）、第 5 章（运行时）、第 9 章（监控告警）。本章是它们的专题深挖，不再重复基础概念。

1. 为什么单独立专题 ​

前面 9 章按「链路」组织（加载 → 渲染 → 运行时），但企业实战中问题以症状出现：用户说「白屏 3 秒」「滑动卡成 PPT」。症状往往横跨多段链路——白屏可能是网络、解析、执行、数据任一层的尾部延迟叠加。本章按症状重组知识，给出三样前面没有的东西：

  • 度量方法：白屏时间、掉帧率这类「非标准指标」怎么采集；
  • 根因分类树：症状到链路的系统映射，避免凭感觉优化；
  • 线上闭环：本地诊断（第 8 章）之外的线上采集、归因与治理流程。

2. 白屏治理：度量先行 ​

白屏时间 ≠ FCP。FCP 只告诉你「第一个像素何时出现」，SPA 里常见「FCP 正常但用户仍觉得白屏」——壳渲染出来了，内容区还是空的。企业级度量需要双指标：

指标含义采集方式
白屏时间（FP 口径）从导航到首次绘制的纯空白时长Performance API 的 first-paint 条目
首屏有效渲染时间首屏关键内容（非壳）实际出现的时间MutationObserver 监听关键容器
js
// 文件: src/monitor/blank-screen.js —— 白屏双指标采集
// ① 白屏时间：paint 条目直接拿（兼容降级用 navigationStart 近似）
const [fp] = performance.getEntriesByType("paint");
const blankTime = fp ? fp.startTime : 0;

// ② 首屏有效渲染：监听首屏容器首次出现「有效子节点」的时刻
function observeMeaningfulPaint(selector, onDone) {
  const target = document.querySelector(selector);
  if (!target) return;
  const observer = new MutationObserver(() => {
    // 有效 = 容器内出现文本或图片，而非只有骨架占位
    if (target.querySelector("img, p, h1, h2, li")) {
      observer.disconnect();
      onDone(performance.now());
    }
  });
  observer.observe(target, { childList: true, subtree: true });
}

observeMeaningfulPaint("#app-main", (meaningfulTime) => {
  report({ metric: "blank_screen", fp: blankTime, meaningful: meaningfulTime });
});

运行方式：入口文件尽早引入（必须在首屏渲染前启动监听）；report 复用第 2 章第 7 节的上报管道。骨架屏会触发 MutationObserver，所以判定条件要排除占位节点（骨架通常有统一 class，可加 not(.skeleton) 过滤）。

监控看板上按「路由 × 设备档位」看 meaningful 的 p75/p98——p98 劣化通常是低端机 + 慢网的叠加，p75 劣化才是版本回归。

3. 白屏治理：根因四级分类与手段矩阵 ​

拿到度量后按四级分类定位，每一级对应前面章节的一组成熟手段，本章不再展开细节，只给映射：

text
白屏症状
├─ ① 网络层：TTFB 慢 / 关键资源晚发现 / 无缓存
│    └▶ CDN 边缘缓存、preload/fetchpriority（第 3 章 2/3/7 节）
├─ ② 解析层：阻塞 CSS 过大 / JS 阻塞首屏
│    └▶ 关键 CSS 内联、defer/module（第 3 章 1 节）
├─ ③ 执行层：bundle 过大、初始化长任务、瀑布式 import
│    └▶ 路由级分割、去副作用初始化（第 3 章 6 节、第 5 章 2 节）
└─ ④ 数据层：首屏接口慢 / 串行请求瀑布 / 鉴权重定向
     └▶ 接口聚合（BFF）、并行预取、loading 数据随 HTML 下发（本节）

数据层是企业项目最常见的白屏元凶，三个高性价比手段：

  1. 接口预取前置：路由解析的同时就发起数据请求，不等组件挂载（Vue 用路由守卫、React 用 loader 模式，React Router v6.4+ / TanStack Router 原生支持）；
  2. HTML 内联首屏数据：SSR/预渲染场景把首屏数据序列化进 window.__INITIAL_STATE__，客户端 hydrate 直接复用，消灭首屏接口往返；
  3. 消灭瀑布：梳理首屏请求的依赖图，无依赖的全部并行；有依赖的把上游结果随 HTML 或 preload 下发。

4. 骨架屏工程化 ​

骨架屏解决的是「白屏的体感」而非白屏本身——它不减指标，但显著降跳出。工程化的三个要点：

  • 等高防 CLS：骨架尺寸必须与真实内容一致，否则骨架消失即布局偏移（第 2 章第 6 节的坑）；
  • 构建时生成：手写骨架易与真实结构漂移，用插件自动生成——Vue 生态 vue-content-loader、React 生态 react-loading-skeleton，或 page-skeleton-webpack-plugin 这类从页面结构自动推导的方案；
  • 首屏直出：骨架 HTML/CSS 内联进 index.html 或随 SSR 首屏下发，不要等 JS bundle 加载完才渲染骨架——否则骨架自己也被白屏。
html
<!-- 文件: index.html 片段 —— 骨架直出：壳 + 骨架随 HTML 首字节到达即渲染 -->
<body>
  <div id="app">
    <!-- SSR 或构建期注入的骨架，客户端挂载时整体替换 -->
    <div class="skeleton" style="height: 200px"><!-- 与真实头图等高 --></div>
  </div>
  <style>
    /* 骨架样式随 HTML 内联，约 1~2KB，不占首屏 JS 预算 */
    .skeleton { animation: pulse 1.5s ease-in-out infinite; background: #eee; }
  </style>
</body>

5. 渲染模式决策树：CSR / SSR / SSG / 预渲染 ​

白屏治理到顶的结构性手段是换渲染模式。企业选型按内容形态决策，不要为 SSR 而 SSR：

text
首屏内容是否千人千面？
├─ 否（营销页/文档/博客）─▶ SSG 静态生成，白屏天然最优，CDN 直接发 HTML
└─ 是
   ├─ 更新频率低、用户量级可控 ─▶ 预渲染（构建期跑一遍页面存 HTML）
   └─ 千人千面 + 高频
      ├─ 首屏数据可聚合、有 SEO 诉求 ─▶ SSR（首选流式 SSR，见下）
      └─ 纯内部系统、无 SEO ─▶ CSR + 骨架屏 + 数据预取（第 4 节）

流式 SSR 是 SSR 场景的进一步白屏优化：不等全部数据就绪，先把壳与已就绪部分 flush 给浏览器，慢数据区块后续以流补齐（Vue 3 的 renderToWebStream、React 18 的 renderToPipeableStream + Suspense）。TTFB 与首屏体感同时受益，是千万级产品的标准配置。

两条企业教训：SSR 引入服务端渲染耗时（Server TTFB），接口慢会原样传导，必须配合第 3 节的接口聚合；流式 SSR 要求 CDN/网关支持分块传输且不做全量缓冲，上线前先验证链路。

6. GPU 加速深挖：合成层的代价 ​

第 4 章讲了「transform/opacity 动画走 GPU 合成最快」，企业级场景必须补上下半句：合成层不是免费的，每一层都占显存。

层爆炸（Layer Explosion） ​

合成层的位图按「宽 × 高 × 4 字节」占内存，一个全屏层在 2x 屏上约 12MB。常见踩坑：

css
/* ❌ 反例：给列表每一项都上 will-change，几百个合成层直接打爆显存 */
.list-item { will-change: transform; }

/* ✅ 正解：只在动画进行时提升，结束后移除 */
.list-item.animating { will-change: transform; }

移动端 Safari 显存超限的表现是页面直接闪白重载（jetsam 回收），线上会被误判成「白屏 bug」——这也是白屏监控要分设备档位看的原因之一。

隐式合成与层压缩 ​

你不知道的提升最危险：A 元素提升为合成层后，所有 z-index 更高且与其重叠的元素会被连带提升（隐式合成）。浏览器会做层压缩（layer squashing）合并部分层，但合并逻辑不可控。排查工具：

  • DevTools → More tools → Layers 面板：3D 视图看层数量与每层内存占用；
  • chrome://gpu：确认 GPU 光栅化是否生效（低端机/驱动黑名单会回退软件光栅化，「GPU 加速」静默失效）；
  • Rendering 面板勾选 Layer borders：页面上的色块边界即层边界。

三条军规 ​

  1. will-change 用完即移除，常驻场景一个页面不超过个位数；
  2. 大面积滤镜（backdrop-filter、大面积 box-shadow）是光栅化杀手，比层数量更常见地导致滚动掉帧；
  3. 「GPU 加速」只对合成阶段生效——JS 长任务、重排照样卡，GPU 治不了主线程的病。

7. GPU 加速深挖：Canvas / WebGL / WebGPU 选型 ​

CSS 合成层管「界面动画」，数据密集型渲染（万级点位、图表、3D）要往下走一层。选型矩阵：

方案适用规模编程模型企业场景
DOM/SVG≤ 千级节点声明式，可访问性好常规业务界面
Canvas 2D千~万级命令式，CPU 光栅化为主简单图表、海报生成
OffscreenCanvas + Worker万级，要求不卡主线程Canvas 放进 Worker 渲染大数据表格可视化、实时曲线
WebGL / Three.js万~百万级GPU 着色器管线3D 场景、大规模散点、地理可视化
WebGPU百万级 + 并行计算计算着色器，现代 APIAI 推理可视化、粒子仿真（新基建，渐进采用）
js
// 文件: src/charts/offscreen-chart.js —— 主线程只移交控制权，渲染不阻塞交互
const canvas = document.querySelector("#big-chart");
const offscreen = canvas.transferControlToOffscreen();
const worker = new Worker("./chart-worker.js");
// 尺寸/数据变更时 postMessage，Worker 内部用 Canvas 2D/WebGL 渲染
worker.postMessage({ canvas: offscreen, data: points }, [offscreen]);

运行方式：transferControlToOffscreen 只能调一次；Worker 内无 DOM API，所有输入靠 postMessage。兼容降级：不支持时回退主线程 Canvas。

两条选型军规：不要为用 WebGL 而用——DOM 能扛住的场景上 WebGL 是引入可维护性灾难；万级以上点位先尝试 OffscreenCanvas（成本低、可访问性损失小），确认瓶颈再上 WebGL/WebGPU。

8. 卡顿线上监控：采集与上报 ​

第 8 章的本地诊断解决不了「用户端真实卡顿分布」。线上采集三件套：

js
// 文件: src/monitor/jank.js —— 卡顿线上采集：长任务 + 掉帧率
// ① 长任务：Long Tasks API，>50ms 即记录，带归因信息
new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    report({
      metric: "long_task",
      duration: entry.duration,
      // attribution 给出容器/脚本来源，是线上归因的关键字段
      source: entry.attribution?.[0]?.containerName || "unknown",
      route: location.pathname,
    });
  }
}).observe({ entryTypes: ["longtask"] });

// ② 掉帧率：rAF 测相邻帧间隔，>32ms（跌破 30fps）记一次掉帧
let last = performance.now();
function frameTick(now) {
  if (now - last > 32) report({ metric: "frame_drop", gap: now - last, route: location.pathname });
  last = now;
  requestAnimationFrame(frameTick);
}
requestAnimationFrame(frameTick);

// ③ INP 归因：web-vitals 的 attribution 构建直接给出交互目标与耗时分解
import { onINP } from "web-vitals/attribution";
onINP(({ value, attribution }) => {
  report({ metric: "inp", value, target: attribution.interactionTarget });
});

运行方式：采样率控制在 5~10%（长任务在高频交互页面量大）；页面隐藏时 rAF 暂停，gap 会产生超大值，上报前过滤 document.hidden。

聚合口径与第 9 章 RUM 一致：按 route × 设备档位 × 版本 分片算 p75/p98。卡顿没有单一阈值，看分布尾部——p98 长任务时长是低端机体验的真实写照。

9. 卡顿归因与治理闭环 ​

线上告警（p98 长任务 > 300ms 连续两天）触发后的标准归因流程：

  1. 圈定范围：按分片维度找到劣化最重的「路由 × 设备 × 版本」组合，关联发版记录；
  2. 线下复现：用 DevTools 的 CPU 4x/6x 降速模拟低端机，在该路由复现长任务；
  3. 火焰图定位：Performance 面板存档，按第 5 章方法归类（长任务/重排/GC/内存）；
  4. 修复与验证：按章节索引选手段（输入卡顿 → 第 7 章并发特性；重任务 → 第 5 章切片/Worker；渲染卡顿 → 第 4 章），灰度放量对比 RUM 数据后全量；
  5. 沉淀：归因结论回填监控看板的「已知问题」注解，下次同类告警直接给修复参考。

卡顿治理与白屏治理共用同一套门禁：第 9 章的 CI 门禁防增量回归，本章的线上采集守存量体验，两者合起来才是完整闭环。

10. 落地检查清单 ​

按症状入口，全部跑通即具备企业级治理能力：

  • [ ] 白屏双指标（FP + 首屏有效渲染）采集上线，按路由 × 设备分片可看
  • [ ] 首屏接口完成依赖梳理：无依赖全并行、上游结果随 HTML 下发
  • [ ] 骨架屏构建时生成、随 HTML 直出、与真实内容等高
  • [ ] 渲染模式按决策树评审过一遍，SSR 场景已启用流式
  • [ ] Layers 面板审计过核心页面，无层爆炸、无常驻 will-change
  • [ ] 大面积滤镜/阴影场景完成光栅化耗时排查
  • [ ] 万级以上数据渲染完成 OffscreenCanvas/WebGL 选型评审
  • [ ] 长任务 + 掉帧率 + INP 归因线上采集（带采样率）上线
  • [ ] 卡顿告警接入第 9 章 RUM 看板，归因五步法写入团队规范
