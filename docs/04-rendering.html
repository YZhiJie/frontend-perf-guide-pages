1. 渲染管线四道工序

浏览器把 DOM 变成屏幕像素，要过四道工序：

Style（计算样式） → Layout（重排：算几何位置） → Paint（重绘：填像素） → Composite（合成：图层叠加出帧）
  • Style：把 CSS 规则匹配到每个元素，算出最终样式；
  • Layout：计算每个元素的几何信息（位置、大小）；
  • Paint：把元素的绘制指令填充成位图；
  • Composite：把各图层合并成最终画面（由 GPU 承担，最快）。

改样式不一定走完全部工序——改的属性决定从哪一步开始重跑，这就是下一节的成本阶梯。

2. 重排、重绘与合成的成本阶梯

层级 触发属性示例 成本 原因
重排（Layout） width height top left margin font-size 最贵 几何变了，后续全部工序重跑，且会传染子孙元素
重绘（Paint） color background border-color visibility 中等 只重跑 Paint 及之后
合成（Composite） transform opacity filter 最便宜 只重跑 Composite，可由 GPU 完成

核心优化思想：把动画从重排层级搬到合成层级。

/* 文件: styles.css —— 同样的视觉位移，成本差一个数量级 */

/* ❌ 反例：动画 top/left，每帧都触发 Layout + Paint */
.box-bad { transition: top 0.3s; position: absolute; top: 0; }
.box-bad.active { top: 200px; }

/* ✅ 正解：动画 transform，每帧只走 Composite（GPU 合成） */
.box-good { transition: transform 0.3s; }
.box-good.active { transform: translateY(200px); }

运行方式：DevTools Performance 面板录制两种动画，对比紫色（Layout）与绿色（Composite）条的存在与否。

完整属性分级表可查 CSS Triggers（csstriggers.com）；拿不准时优先用 transform: translate/scale/rotate 表达位移缩放旋转。

3. 强制同步布局与布局抖动

强制同步布局（Forced Synchronous Layout）：JS 在同一帧里「读布局属性 → 写样式 → 再读 → 再写」交替进行，每次写都会让刚读的布局失效，浏览器被迫反复重排。

// 文件: 示例片段 —— 布局抖动 ❌ 与批量读写 ✅

// ❌ 反例：读写交替，N 个元素触发 N 次重排
items.forEach((el) => {
  const top = el.offsetTop;       // 读（强制浏览器重排，让刚写的样式生效）
  el.style.transform = `translateY(${top + 10}px)`; // 写（布局失效）
});

// ✅ 正解：先批量读完，再批量写，全程只重排 1 次
const tops = items.map((el) => el.offsetTop);      // 全部读
items.forEach((el, i) => {
  el.style.transform = `translateY(${tops[i] + 10}px)`; // 全部写
});

运行方式：两种写法分别录制 Performance（完整对比 demo 见 examples/03-layout-thrashing.html），观察紫色 Layout 条从连续锯齿变为一根。

常见「隐形读」API 都要警惕：offsetTop/offsetWidth、getBoundingClientRect()、getComputedStyle()、clientHeight 等。

4. 合成层与 will-change

把频繁变化的元素提升为独立合成层，它重绘时不牵连整页，由 GPU 独立合成——这就是动画提速的原理。

/* 文件: styles.css —— 合成层的正确打开方式 */
.modal {
  /* 浏览器提前为将要变化的属性做准备（创建独立图层） */
  will-change: transform;
  transition: transform 0.25s;
}

三条使用纪律：

  1. 加在确实频繁变化的元素上，随动画结束移除；每个图层都要占显存；
  2. 层爆炸（Layer Explosion）：给几百个元素都 will-change: transform，显存直接爆掉，反而更卡。用 DevTools Layers 面板检查图层数量与内存；
  3. 静态元素不要加 will-change——它没有「预优化」作用，只有成本。

💡 经验法则：先测量（Layers/Performance 面板确认瓶颈在 Paint），再提层，而不是「感觉卡就加 will-change」。

5. 主线程与长任务

主线程一次执行超过 50ms 的任务就是长任务（Long Task）——期间无法响应任何输入，直接推高 INP。

检测与拆解：

// 文件: 示例片段 —— 用 PerformanceObserver 监控长任务（生产可上报）
new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    console.warn('长任务:', Math.round(entry.duration), 'ms');
    // 上报到监控系统：duration、startTime、attribution
  }
}).observe({ type: 'longtask', buffered: true });

任务切片：把大计算拆成小步，每步之间让出主线程（完整说明见第 5 章第 2 节）：

// 文件: 示例片段 —— 切片处理 1 万条数据，每步后主线程可响应用户输入
async function processAll(items) {
  const CHUNK = 200; // 每批 200 条，单批控制在 50ms 内
  for (let i = 0; i < items.length; i += CHUNK) {
    items.slice(i, i + CHUNK).forEach(process);
    await new Promise((r) => setTimeout(r)); // 让出主线程（Chrome 129+ 可用 scheduler.yield()）
  }
}

运行方式：浏览器运行，Performance 面板可见原本 3s 的整块长任务变为多个小任务块。

6. 防抖、节流与 rAF 节流

高频事件（scroll/resize/input/mousemove）必须限频，三种策略：

策略 行为 适用
防抖 debounce 停止触发后延迟 N ms 执行一次 搜索输入、resize 重算
节流 throttle 每 N ms 最多执行一次 滚动加载、按钮防重复点击
rAF 节流 每帧最多执行一次，与渲染对齐 滚动驱动的视觉更新（最推荐） 
// 文件: src/utils/raf-throttle.js —— rAF 节流：视觉更新与帧对齐，不产生中间废帧
export function rafThrottle(fn) {
  let ticking = false;
  return function (...args) {
    if (ticking) return;
    ticking = true;
    requestAnimationFrame(() => {
      fn.apply(this, args);
      ticking = false;
    });
  };
}

// 用法：滚动视差/吸顶计算等「必须每帧同步视觉」的场景
window.addEventListener('scroll', rafThrottle(() => {
  header.style.transform = `translateY(${Math.min(window.scrollY, 64)}px)`;
}), { passive: true }); // passive: 告诉浏览器不会 preventDefault，滚动不被 JS 阻塞

运行方式：任意页面引入并滚动，Performance 面板确认回调频率与帧率一致。

7. 虚拟列表与 content-visibility

虚拟列表：1 万条数据只渲染可视区的 20 条，DOM 规模恒定。原理：滚动容器 + 顶部占位（撑起总高度）+ 绝对定位渲染可视窗口（按 滚动距离 / 行高 计算起止下标）。

// 文件: 示例片段 —— 虚拟列表核心计算（生产建议用成熟库）
function getVisibleRange(scrollTop, viewportH, rowH, total) {
  const start = Math.max(0, Math.floor(scrollTop / rowH) - 5);      // 上下各多渲染 5 行缓冲
  const end = Math.min(total, Math.ceil((scrollTop + viewportH) / rowH) + 5);
  return { start, end, offsetY: start * rowH };
}

运行方式：Vue 用 vue-virtual-scroller、React 用 react-window（API 更完整，处理动态行高/树形等）。

content-visibility：CSS 层面的「浏览器原生懒渲染」，长页面中视口外的区块跳过渲染，几乎零 JS 成本：

/* 文件: styles.css —— 长列表/长文章区块的浏览器级懒渲染 */
.section {
  content-visibility: auto;
  contain-intrinsic-size: auto 500px; /* 占位高度估算值，防止滚动条跳动（防 CLS） */
}

运行方式：Chrome 打开长页面录制 Performance，对比启用前后 Layout/Paint 耗时。

8. 框架落地：v-memo 与 React.memo

框架的渲染优化本质都是跳过没有变化的更新：

Vue 3：v-memo 给模板加缓存——依赖数组不变时跳过整段 VNode 渲染：

<!-- 文件: src/components/List.vue 片段 —— 大列表行组件：仅当 item 变化或选中项变化时重渲染 -->
<template>
  <div v-for="item in list" :key="item.id" v-memo="[item.id === selectedId]">
    <span>{{ item.name }}</span>
    <span>{{ item.detail }}</span>
  </div>
</template>

React：React.memo 包组件 + 稳定的 props 引用（useMemo/useCallback）：

// 文件: src/components/Row.jsx —— props 不变则跳过重渲染
const Row = React.memo(function Row({ item, onSelect }) {
  return <li onClick={() => onSelect(item.id)}>{item.name}</li>;
}, (prev, next) => prev.item === next.item); // 可选：自定义浅比较

function List({ items }) {
  const onSelect = useCallback((id) => select(id), []); // 稳定引用，否则 memo 失效
  return <ul>{items.map((it) => <Row key={it.id} item={it} onSelect={onSelect} />)}</ul>;
}

⚠️ 共同的坑：先确认「确实有无效重渲染」再上缓存。用 Vue DevTools 的渲染高亮、React DevTools Profiler 定位到具体组件，而不是全站乱包 memo（比较本身也有成本）。系统性方法论见第 6/7 章。

9. 最佳实践清单

  • 动画只用 transform/opacity，禁止动画 top/left/width/height
  • 批量读写分离，消灭循环内的强制同步布局
  • will-change 只加在实测有瓶颈的频繁变化元素上，用完移除
  • 大计算切片（scheduler.yield()/setTimeout），单块任务 ≤ 50ms
  • 高频事件：视觉更新用 rAF 节流 + passive: true，逻辑触发用防抖/节流
  • 万级数据列表上虚拟滚动；长页面静态区块用 content-visibility: auto
  • 框架层先测量再缓存：Vue v-memo/React memo 只用于确认的无效渲染热点
