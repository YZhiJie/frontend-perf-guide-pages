1. 重渲染的触发链条

组件重渲染只有三个触发源：自身 state 变化、父组件重渲染（props 未变也会）、消费的 context 变化。关键事实：

  • 一个组件重渲染时，默认递归重渲染它的全部子树——子组件 props 没变也照样重跑函数体与 diff；
  • 重渲染的成本 = 函数体执行 + VNode diff + 可能的 DOM commit，组件树越大越贵；
  • Profiler 先行：React DevTools Profiler 录制一次交互，按「耗时排序」找出真热点，再动手优化。
// 文件: 示例片段 —— 用 Profiler API 在生产环境量化组件渲染
import { Profiler } from 'react';

<Profiler id="FeedList" onRender={(id, phase, duration) => {
  if (duration > 16) reportToMonitor({ id, phase, duration }); // 超一帧的渲染上报
}}>
  <FeedList items={items} />
</Profiler>

运行方式：日常定位用 React DevTools Profiler 面板（火焰图按耗时着色）；线上监控用 Profiler API 上报。

2. 渲染控制三件套：memo useMemo 与 useCallback

三件套各自只做一件事，必须组合使用才生效：

API 缓存什么 单独用的效果
React.memo(Comp) 组件的渲染结果（props 浅比较） 函数 props 每次都是新引用 → memo 形同虚设
useMemo(fn, deps) 值（计算结果/对象/数组引用） 只省重算，不阻止子组件重渲染
useCallback(fn, deps) 函数引用 只省函数创建，不阻止子组件重渲染 
// 文件: src/components/Feed.jsx —— 标准组合：memo 子组件 + 稳定引用 props
const FeedCard = memo(function FeedCard({ item, onLike }) {
  return (
    <article onClick={() => onLike(item.id)}>
      <h3>{item.title}</h3>
      <p>{item.summary}</p>
    </article>
  );
});

function Feed({ items }) {
  const [liked, setLiked] = useState(new Set());
  // useCallback 稳定函数引用 → FeedCard 的 memo 才能命中
  const onLike = useCallback((id) => {
    setLiked((prev) => new Set(prev).add(id));
  }, []);

  // useMemo 缓存派生数组：items 不变时过滤不重算，引用也稳定
  const visible = useMemo(() => items.filter((it) => it.status === 'ok'), [items]);

  return visible.map((it) => <FeedCard key={it.id} item={it} onLike={onLike} />);
}

⚠️ 滥用的代价：三件套本身有比较与缓存成本。Profiler 没证明是热点之前，不要全站包裹——「先测量再优化」在这里同样成立。

3. 状态下放与组件组合

比 memo 更根本的优化是调整结构，让重渲染范围天然变小：

① 状态下放：状态放在「使用它的组件的最小公共父级」，而不是统一塞顶层：

// 文件: src/components/Search.jsx 片段 —— 状态下放
// ❌ inputText 放在 Page 顶部：每敲一个字整个页面重渲染
// ✅ 状态收进只含输入框和结果的 SearchBar 内部，页面其他部分纹丝不动
function SearchBar() {
  const [text, setText] = useState('');
  return <><input value={text} onChange={(e) => setText(e.target.value)} /><Results q={text} /></>;
}

② 组合模式（children 穿透）：把「不变的组件」作为 children 传入，父组件重渲染时 children 是同一个引用，直接跳过：

// 文件: src/components/ScrollTracker.jsx —— 经典组合技巧
function ScrollTracker({ children }) {
  const [y, setY] = useState(0);
  useEffect(() => {
    const onScroll = () => setY(window.scrollY);
    window.addEventListener('scroll', onScroll, { passive: true });
    return () => window.removeEventListener('scroll', onScroll);
  }, []);
  // children 从外部传入：ScrollTracker 因 y 变化重渲染时，
  // children 引用不变 → 传进来的昂贵组件完全跳过重渲染
  return <div data-y={y}>{children}</div>;
}

<ScrollTracker><ExpensiveTree /></ScrollTracker>

③ Context 拆分：context 值一变，所有消费者重渲染。高频变化的（如光标位置）与低频的（主题、用户信息）拆成两个 context。

4. 列表渲染与 key 的正确用法

key 让 React 识别「谁是谁」，key 错 = 性能与正确性双输：

// 文件: 示例片段 —— key 的对与错
// ❌ 用数组下标当 key：删除中间项后，后续所有项的 key 前移，
//    React 认为每一项都「变了」→ 全列表重渲染；带输入框等内部状态时会状态错位
{todos.map((t, i) => <Todo key={i} todo={t} />)}

// ✅ 用稳定唯一的业务 id：删除一项只影响那一项
{todos.map((t) => <Todo key={t.id} todo={t} />)}

// ✅ 进阶：刻意用 key 重建子树（如搜索条件变化时重置内部状态）
<UserProfile key={userId} userId={userId} />

5. 代码分割：lazy 与 Suspense

React 的路由级分割由 lazy + Suspense 组合完成（与第 3 章第 8 节呼应）：

// 文件: src/App.jsx —— 路由级代码分割
import { lazy, Suspense } from 'react';

// 首屏组件正常 import；二级页面动态加载，自动拆出独立 chunk
const Admin = lazy(() => import('./views/Admin'));
const Report = lazy(() => import('./views/Report'));

export default function App() {
  return (
    <Suspense fallback={<PageSkeleton />}>
      <Routes>
        <Route path="/admin" element={<Admin />} />
        <Route path="/report" element={<Report />} />
      </Routes>
    </Suspense>
  );
}

运行方式：npm run build 后查看 dist 的 chunk 拆分；fallback 给骨架屏而非空白，兼顾 CLS（骨架尺寸与内容一致）。

进阶：对「用户大概率会点」的路由，在空闲时预加载：const preload = () => import('./views/Report'); 配合 onMouseEnter 或 requestIdleCallback 触发。

6. 并发特性：useTransition 与 useDeferredValue

React 18+ 的并发特性解决「更新本身太重」导致的交互卡顿（输入延迟，INP 杀手）：

// 文件: src/components/BigFilter.jsx —— 输入 + 万级列表过滤的标准解法
import { useState, useTransition, useDeferredValue } from 'react';

function BigFilter({ items }) {
  const [query, setQuery] = useState('');
  const [isPending, startTransition] = useTransition();

  // 方案 A：useDeferredValue——给 query 一个「延迟版本」，
  // 输入框立即响应（高优），大列表用旧值先渲染、新值低优渲染
  const deferredQuery = useDeferredValue(query);

  // 方案 B：startTransition——把重更新标记为可中断的非紧急更新
  function onChange(e) {
    setQuery(e.target.value);                    // 紧急：输入框内容立即更新
    startTransition(() => {
      setResult(filter10k(items, e.target.value)); // 非紧急：可被新输入打断
    });
  }

  return (
    <>
      <input value={query} onChange={onChange} />
      {isPending && <span>计算中…</span>}
      <List q={deferredQuery} />
    </>
  );
}

运行方式：React 18+ 项目内对比使用前后的输入跟手度；用 DevTools Performance 录制确认输入事件不再被大计算阻塞。

选型：输入类优先 useDeferredValue（写法最简）；多状态联动的重更新用 startTransition 显式标记。

7. 状态管理的订阅粒度

Context 是「全量订阅」：值变，所有消费者重渲染。外部状态库的正确姿势是按字段订阅（selector）：

// 文件: src/store.js —— zustand 按字段订阅（Redux useSelector 同理）
import { create } from 'zustand';

const useStore = create((set) => ({
  user: null, posts: [], theme: 'light',
  setTheme: (theme) => set({ theme }),
}));

// ❌ 整店订阅：任何字段变化都触发重渲染
const { user, posts, theme } = useStore();

// ✅ 按字段 selector：只有 user 变化时本组件才重渲染
const user = useStore((s) => s.user);

原则：组件订阅它渲染所需的字段，不多不少；列表类数据配合 shallow 比较或多 atom 拆分，避免「改一条导致全列表订阅者更新」。

8. React 19：Compiler 与自动记忆化

React 19 引入 React Compiler（构建期编译器，babel-plugin-react-compiler）：自动分析组件，自动插入等价于 useMemo/useCallback/memo 的记忆化，手写三件套的场景大幅减少：

// 文件: vite.config.ts 片段 —— 启用 React Compiler
import react from '@vitejs/plugin-react';

export default defineConfig({
  plugins: [react({ babel: { plugins: [['babel-plugin-react-compiler', {}]] } })],
});

启用 Compiler 后的正确心态：

  1. 结构优化仍是根本：状态下放、组合模式、selector 订阅，Compiler 一样也替代不了；
  2. 代码需符合 Rules of React（纯渲染），违反规则的模式 Compiler 会自动跳过优化（用 eslint-plugin-react-hooks 检查）；
  3. 已有的 useMemo/useCallback 可以保留（编译器会识别并兼容），逐步清理。

9. 最佳实践清单

  • 优化前先跑 React DevTools Profiler，热点组件用数据说话
  • memo/useMemo/useCallback 组合使用才有意义，禁止全站无脑包裹
  • 状态放最小公共父级；不变的子树用 children 组合穿透
  • Context 按变更频率拆分，高频状态改用 selector 订阅
  • 列表 key 用稳定业务 id，禁用数组下标
  • 路由级 lazy + Suspense 全覆盖，fallback 用等高骨架屏
  • 输入卡顿用 useDeferredValue，重更新用 startTransition
  • React 19 项目评估启用 Compiler，但结构优化不外包
