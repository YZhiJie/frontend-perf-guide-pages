第 8 章 · 性能检测工具完全指南 ​

1. 工具全景：选对工具做对事 ​

工具类型回答的问题使用场景
Lighthouse实验室快照「这个页面整体几分，该改什么」快速体检、改进清单
DevTools Performance实验室精查「具体哪段代码/哪一帧卡」定位长任务、布局抖动
DevTools Network实验室精查「哪些资源慢、优先级对不对」加载问题溯源
WebPageTest可控真实环境「换个地点/网络/设备还快吗」弱网与地域矩阵测试
web-vitals + RUM真实用户「我的真实用户体验到底如何」业务结论、回归告警
Lighthouse CI流水线「这次提交有没有让性能变差」CI 门禁

💡 心法：实验室找病因，真实数据下诊断。所有实验室工具都无法替代真实用户监控。

2. Lighthouse：从跑分到改进项 ​

三种跑法，CLI 最适合自动化与批量：

bash
# 文件: 终端命令 —— Lighthouse CLI 跑移动端模拟（Chrome 需已安装）
npx lighthouse https://example.com \
  --preset=perf \
  --form-factor=mobile \
  --screenEmulation.mobile \
  --output=html --output-path=./lh-report.html \
  --chrome-flags="--headless"

# 桌面端口径
npx lighthouse https://example.com --preset=desktop --output=json --output-path=./lh.json --chrome-flags="--headless"

运行方式：直接执行；--quiet 静默输出，--only-categories=performance 只跑性能类。

报告解读三步：

  1. 看性能分构成：Lighthouse 10 的性能分由五项加权——TBT 30%、LCP 25%、CLS 25%、FCP 10%、SI 10%。先修权重高的（TBT/LCP/CLS）；
  2. 看「Opportunities/诊断」区：按预估节省时间排序的改进项（如「启用文本压缩 可省 1.2s」），逐项落地；
  3. 区分模拟与实测：Lighthouse 移动端默认是模拟节流（Moto G4 + 慢速 4G + 4 倍 CPU 降速），数字用于横向对比，不等于真实用户。

三个常见误读：

  • 分数每次波动 ±5 分属正常（环境噪声），要看趋势与多次中位数，别纠结单次；
  • 「性能分 90」不等于「真实用户体验好」——它测的是单页单环境快照；
  • 插件/登录态会显著改变结果，测试统一用无痕模式 + 无插件。

3. Lighthouse CI：把分数关进流水线 ​

bash
npm install -g @lhci/cli
js
// 文件: lighthouserc.js —— Lighthouse CI 配置：连跑 3 次取稳定值，低于阈值即失败
module.exports = {
  ci: {
    collect: {
      staticDistDir: './dist',      // 或 url 列表：url: ['https://example.com']
      numberOfRuns: 3,              // 多次运行抵消波动
    },
    assert: {
      assertions: {
        'categories:performance': ['error', { minScore: 0.85 }],
        'largest-contentful-paint': ['error', { maxNumericValue: 2500 }],
        'cumulative-layout-shift': ['error', { maxNumericValue: 0.1 }],
        'total-byte-weight': ['warn', { maxNumericValue: 3 * 1024 * 1024 }],
      },
    },
  },
};
bash
# 文件: 终端命令 —— 本地与 CI 中执行（见第 9 章流水线接入）
npx lhci autorun

运行方式：先 npm run build 再 npx lhci autorun；断言失败会以非零退出码拦截流水线。

4. Performance 面板：火焰图精读 ​

DevTools Performance 面板是定位「哪段代码卡」的核心武器。标准操作流：

  1. 先设节流（模拟用户环境）：CPU 4x slowdown + Network Slow 4G；
  2. 录制：点击录制 → 执行用户操作（滚动/点击/输入）→ 停止；
  3. 读轨道（自上而下：Timings → Interactions → 主线程火焰图 → 帧率）。

火焰图读图要点：

看什么识别特征结论
长任务主线程上 >50ms 的整块，右上角红色三角点开 Bottom-Up 按 Self Time 排序找元凶函数
布局抖动连续的紫色 Layout 锯齿（本教材第 4 章第 3 节）读写分离重构
掉帧Frames 轨道出现红色帧 / FPS 曲线下探结合上方两项定位
GC 频繁主线程密集的 GC 条纹内存问题，转 Memory 面板（第 5 章）
强制同步布局函数名旁紫色「Recalculate Style — forced reflow」标记读布局 API 的调用点

💡 Bottom-Up（自下而上）视图按 Self Time（自身耗时） 排序，是「找到那个函数」最快的路径；Call Tree 则回答「它是被谁调用的」。

5. Network 面板：瀑布图与优先级 ​

加载问题的第一现场。关键动作：

  1. 勾选 Disable cache，选 Slow 4G 节流，刷新录制；
  2. Waterfall 列读时序：横条越长下载越久；斜向阶梯（一条接一条）说明存在串行阻塞——典型如「HTML → CSS → 字体 → 渲染」的链式等待；
  3. Priority 列看优先级：LCP 主图应是 High（否则加 fetchpriority="high"，见第 3 章）；被降级的预加载资源（Preload as=style 但迟迟不用）会触发警告；
  4. 按 Initiator 列追责：这个请求是谁触发的？（往往能定位到某段 JS 才发起请求的问题）；
  5. 导出 HAR 归档对比：优化前后各存一份，逐请求对比 Time 与 Size 变化。

6. WebPageTest：真实网络环境会诊 ​

WebPageTest 提供全球测试节点 + 真实设备/网络档位，补齐 Lighthouse「实验室理想化」的短板：

  • 测试配置：选地点（选目标用户的真实地域）、连接档位（3G/4G/光纤）、机型、测试次数（建议 3+ 次取中位）；
  • First View vs Repeat View：首次访问（冷缓存）与回访（命中缓存）分开看——回访慢说明缓存策略有问题（第 3 章第 7 节）；
  • Filmstrip 视图：逐帧截图，直观看到「白屏多久、内容何时出现、何时可交互」，比数字更能对齐团队认知；
  • 对比测试：把优化前后两条 URL 放进 Compare，瀑布图并排对比，适合做优化汇报材料。

7. RUM 与真实用户数据 ​

采集端在第 2 章第 7 节（web-vitals 上报），这里讲数据消费端——RUM 看板的最小可用形态：

维度内容
聚合口径各指标取 p75（Google 官方口径），同时看 p98 防长尾
分片维度页面路由、设备类型、网络类型、地区——劣化时快速圈定范围
趋势与告警按天趋势 + 环比，p75 连续劣化超阈值（如 10%）触发告警
归因辅助配合 web-vitals 的 attribution 版本上报瓶颈归属（哪个元素/哪一阶段）

💡 没有 RUM 看板的团队，性能优化是盲人摸象：你不知道用户在哪条路上被卡住，也不知道优化上线后是否真的生效。

8. 最佳实践清单 ​

  • [ ] Lighthouse 统一用 CLI + 无痕模式跑，多次取中位数看趋势
  • [ ] 性能分构成记牢：TBT/LCP/CLS 权重最高，优先修它们
  • [ ] Lighthouse CI 接入流水线，断言阈值与性能预算（第 9 章）一致
  • [ ] Performance 录制前先设节流（CPU 4x + Slow 4G），结论才接近真实
  • [ ] 定位函数级瓶颈用 Bottom-Up 的 Self Time 排序
  • [ ] Network 瀑布图排查串行链与优先级错位，HAR 归档做前后对比
  • [ ] WebPageTest 补真实地域/弱网/首访回访视角
  • [ ] RUM 看板以 p75 为口径、可按路由与设备分片、有劣化告警
