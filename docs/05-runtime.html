1. 事件循环：浏览器的时间切片法则

浏览器同一时刻只有一个主线程，靠事件循环调度三类工作：

┌─▶ 执行宏任务（script/setTimeout/事件回调）─▶ 清空全部微任务（Promise.then/queueMicrotask）
│       ─▶ 需要渲染？─▶ rAF 回调 ─▶ Style/Layout/Paint ─▶ Composite
└────────────────────────────── 循环 ◀──────────────────────────────┘

必须记住的三条规则：

  1. 微任务插队：每个宏任务跑完，立即清空整个微任务队列——微任务在渲染之前执行，所以 Promise.then 总是先于 setTimeout（同一轮里）。
  2. 渲染发生在任务之间：一个任务执行多久，用户就卡多久。这就是「50ms 长任务」红线（RAIL 的 Idle 刻度）的由来。
  3. rAF 在渲染前：requestAnimationFrame 回调在本轮渲染之前执行，是做帧同步更新的正确位置。
// 文件: 示例片段 —— 经典执行顺序题（Node 与浏览器一致的核心顺序）
console.log('1 同步');
setTimeout(() => console.log('4 宏任务'));
Promise.resolve().then(() => console.log('3 微任务'));
console.log('2 同步结束');
// 输出：1 → 2 → 3 → 4（同步 → 微任务 → 宏任务）

运行方式：node examples/01-event-loop.mjs（完整版含嵌套场景与逐行注释）。

2. 长任务切分与调度

第 4 章已介绍基本切片，这里补充调度策略——切片不是均分，而是按优先级安排：

// 文件: src/utils/scheduler.js —— 带优先级的任务调度器（生产可用骨架）
const deadlines = { userVisible: 50, background: 5000 };

export async function runChunks(items, fn, { chunk = 200, priority = 'userVisible' } = {}) {
  for (let i = 0; i < items.length; i += chunk) {
    // scheduler.postTask：告知浏览器优先级，让高优任务插队（Chrome 94+）
    if ('scheduler' in window) {
      await scheduler.postTask(() => {}, { priority, delay: 0 }).catch(() => {});
    } else {
      await new Promise((r) => setTimeout(r, 0)); // 回退：宏任务让出主线程
    }
    items.slice(i, i + chunk).forEach(fn);
  }
}

// 用户交互触发的更新用高优先级；埋点上报、预计算用 background 低优先级
runChunks(feedItems, renderCard, { priority: 'userVisible' });
runChunks(trackQueue, send, { priority: 'background' });

运行方式：浏览器运行；Performance 面板确认大任务已拆散且不阻塞输入响应。

配套手段：交互后的非紧急更新用 requestIdleCallback（空闲时执行）；React 项目直接用 useTransition（第 7 章）。

3. V8 内存管理与垃圾回收

JS 内存分栈（原始值、引用指针，函数退出即回收）与堆（对象、闭包捕获的数据，靠 GC 回收）。V8 的堆采用分代回收：

空间 存放 回收器 特点
新生代 短命对象（临时变量、新对象） Scavenger（半空间复制） 高频、极快（毫秒级）
老生代 存活久的对象 Mark-Compact（标记-清除/整理） 低频、较慢，有增量标记减少停顿

对业务的三个推论：

  1. 对象分代迁移有成本：被引用太久的小对象会「晋升」到老生代，晋升越多、老生代越大、主要 GC 越慢——及时断开不再需要的引用就是最好的 GC 优化；
  2. GC 会偷帧：主要 GC 的停顿可能吃掉一帧甚至几帧，内存峰值高的大页面（如一次性渲染 1 万行表格）滚动时容易看到 GC 锯齿；
  3. 大对象要流式处理：几十 MB 的 JSON 不要 JSON.parse 整个塞进内存，分页/分片加载。

4. 四大内存泄漏模式

GC 只回收「不可达」的对象；只要还有一条引用链挂着，内存就永远放不掉。四大泄漏模式：

// 文件: 示例片段 —— 四大内存泄漏模式（生产代码逐条对照自查）

// ① 意外的全局变量：漏写声明，函数退出后数据仍被 window 持有
function bad() { cache = loadData(); }         // ❌ cache 挂到 window，永不回收
function good() { const cache = loadData(); }  // ✅ 局部作用域，用完即回收

// ② 被遗忘的定时器/回调：组件销毁了，定时器还活着并闭包引用着大数据
const timer = setInterval(() => renderWidget(bigData), 1000);
clearInterval(timer); // ✅ 销毁时必须清除（框架内见本章第 7 节）

// ③ 游离 DOM（Detached DOM）：JS 变量还引用着已从页面移除的节点
let detachedBtn = document.querySelector('#btn');
document.body.removeChild(detachedBtn);
detachedBtn = null; // ✅ 移除后置空引用，整个子树才能被回收

// ④ 闭包持有大数据：小函数拽住了大数组
function makeHandler() {
  const hugeList = load100kItems();              // 10 万条数据
  return () => track(hugeList.length);           // ❌ 只用了 length，却拽住整个数组
}
// ✅ 只捕获需要的值
function makeHandlerGood() {
  const total = load100kItems().length;
  return () => track(total);
}

排查三步法（DevTools Memory 面板）：

  1. 做堆快照 A → 执行可疑操作（打开弹窗/翻页）→ 强制 GC（垃圾桶按钮）→ 做快照 B；
  2. 快照 B 按「Objects allocated between A and B」对比，看哪些对象本应释放；
  3. 选中可疑对象看 Retainers 链，找到是谁拽着它——那条链就是泄漏点。

运行方式：泄漏演示与复现脚本见 examples/02-memory-leak.mjs（node --expose-gc 运行）。

5. Web Worker：把重活搬出主线程

判断标准：一类计算稳定地超过 50ms 且与 DOM 无关（大 JSON 解析、复杂排序、图片处理、数据聚合），就该搬进 Worker。偶发的短计算切片即可，不必上 Worker（有通信成本）。

// 文件: src/worker/analytics.worker.js —— 数据聚合在 Worker 中执行
self.onmessage = (e) => {
  const result = heavyAggregate(e.data); // 主线程零阻塞
  self.postMessage(result);
};

// 文件: src/pages/report.js —— 主线程发起与接收
const worker = new Worker(new URL('./worker/analytics.worker.js', import.meta.url));
worker.postMessage(rawRecords);
worker.onmessage = (e) => render(e.data); // 结果回来再更新 UI
// 组件销毁时 terminate()，否则 Worker 线程常驻耗内存

运行方式：Vite 原生支持 new Worker(new URL(...), import.meta.url) 语法，npm run dev 直接可用。

要点：Worker 不能操作 DOM（这是特性不是缺陷——强制你把计算与 UI 分离）；大数据传递用 Transferable（如 ArrayBuffer 转移所有权，零拷贝）。

6. 用 Performance API 给代码掐表

优化前先量化，performance.mark/measure 是标准化的掐表工具：

// 文件: 示例片段 —— User Timing：给关键路径打点，Performance 面板可视化
performance.mark('filter-start');
const filtered = applyFilters(rawRows);   // 疑似瓶颈的函数
performance.mark('filter-end');
performance.measure('筛选耗时', 'filter-start', 'filter-end');

const [m] = performance.getEntriesByName('筛选耗时');
console.log(`${m.name}: ${m.duration.toFixed(1)}ms`); // 与 setInterval 心跳对比定位抖动来源
performance.clearMeasures(); // 清理，避免重复上报

运行方式：浏览器运行后打开 Performance 面板，Timings 轨道会显示这些测量条；node examples/ 中同 API 在 Node 亦可用。

7. 框架落地：组件卸载时的资源清理

内存泄漏在框架项目里最常见的形态：组件销毁了，副作用还活着。两个框架的清理范式：

Vue 3：onUnmounted（或 onScopeDispose）清理；封装成组合式函数一劳永逸：

// 文件: src/composables/useResizeListener.js —— 自动清理的事件订阅
import { onUnmounted } from 'vue';

export function useResizeListener(handler) {
  window.addEventListener('resize', handler, { passive: true });
  // 组件卸载自动移除——调用方不可能「忘记清理」
  onUnmounted(() => window.removeEventListener('resize', handler));
}

React：useEffect 返回清理函数，依赖数组里放定时器外的一切可变引用：

// 文件: src/hooks/usePolling.js —— 轮询 hook：StrictMode 双挂载与卸载都安全
export function usePolling(fn, interval = 5000) {
  useEffect(() => {
    const timer = setInterval(fn, interval);
    return () => clearInterval(timer); // 清理函数：卸载时必执行
  }, [fn, interval]);
}

自查清单：组件里创建过的每一类资源（定时器、事件监听、Observer、Worker、WebSocket、第三方实例），是否都有对应的销毁路径？

8. 最佳实践清单

  • 能背出事件循环顺序：同步 → 微任务 → 渲染前 rAF → 宏任务
  • 所有稳定超 50ms 的计算：切片（交互相关）或 Worker（DOM 无关）
  • 上报 longtask 观测，INP 劣化时先看长任务曲线
  • 四大泄漏模式纳入 Code Review 清单：全局变量、忘清定时器、游离 DOM、闭包大对象
  • 每次发版前用 Memory 面板做一次「操作前后堆快照」对比
  • 框架组件的每个副作用都有销毁路径（组合式函数/hook 封装固化）
  • 大数据流式处理，不做整包 JSON.parse
